## 可直接用于汇报的核心判断

1. AgentFlow 已有通用 C++ 执行底座、Python Agent Harness、独立 trajectory_evolution 组件及可复现实验脚本。自进化主要改变经验注入、动作约束和循环控制，不训练模型权重。
2. 架构是在线固定策略执行 + 后台从轨迹学习/GEPA搜索 + 验收发布回到后续执行，而不是每次请求在热路径做完整搜索。
3. “组件存在”“宿主已接线”“配置启用”“应用回执通过”“同题收益证明”必须单独陈述。尤其模板默认 v2，而专用自进化接线集中 v1，完整 v2 适配和默认环境一致性未验证。
4. 轨迹异常恢复主要恢复已持久化的学习状态/评测检查点，并把不完整业务运行隔离；不应声称故障后会自动从上次工具动作继续原业务。
5. 现有原生打点使用有界内存路径；原生关闭回执不等于落盘。HTTP 若配置 buffered 同样先入内存队列，需用 persisted/flush 验证。

## 2. 一轮请求的完整运行链

可用于 PPT 的图：

```text
用户 / API
  → Bridge chat_rest（user_id / client_id / dialogue_id）
  → JSON-RPC agent.execute / agentflowd
  → AgentRegistry → SessionRouter → Session / Task
  → 工作流 / Scheduler / Worker
  → Python Coordinator(v1) → run_skills manifest
  → C++ Batch：并发槽位、active / queued、ALL join
  → Skill Executor：LLM round → Tool(s) → Host / Sandbox
  → DataBus completion_batch / 业务终态
  → Coordinator 下一次 activation → 最终候选
  → ResponsePoller → Bridge 最终交付 / SessionLog
```

源码证据：

- `frontend/bridge/routes/chat_rest.py:471` 调用 daemon_client.agent_execute，并传 user/client/dialogue；一轮总超时包裹调用。
- `src/daemon/agentflowd_main.cpp:56` 构造/initialize Daemon，`:63` run。

- `src/agent/session_router.cpp:154` handle_route_message，`:175` allocate_session_for_route：按 user_id + client_id 的 route_key 绑定会话；保留 session_hint 所有权校验和初始化等待。

## 5. 可追溯性与状态语义

三个观测面：

1. C++ FlowTrace 记录框架消息/调度；`daemon.cpp:108` 初始化。
2. C++/Python Span Trace 记录节点与耗时；`daemon.cpp:121` 为共用 trace_output_dir 绝对化路径。

## 6. 当前持久化与故障恢复边界

### 原生入口

- `local_runtime.cpp:116` 状态 free_slot→active→closed→writing→persisted。
- `local_runtime.cpp:292` make_run在run开始筛记忆、编译固定PolicyRuntime（`:343` private/public快照，`:368` compile_runtime_policy）。后台新记忆影响后续run，本次run不中途更换策略。
- `local_runtime.cpp:671` drain：`:690` active仅一次保存 slot.initial；`:697` closed才移动最终slot.state写入，`:721` persist_local，`:738` persisted。
- 因此原生成功打点和run.end只意味着在有界内存路径接受；中间事件未逐条增量落盘，SIGKILL/断电可能丢失。
- `local_runtime.cpp:865` destructor停止线程，`:877` 活动槽标 producer_shutdown并closed，`:884` 最后drain。这仅是正常析构可走路径。

### HTTP入口

- `integration_service.cpp:431` 若设置 http_persistence.mode 支持 buffered/durable；只有配置包含此字段时才改buffered_capture，不能把省略字段误判为默认buffered。
- `integration_service.cpp:1330` save：`:1340` buffered且非capture_durable只入有界capture_writes/capture_dirty，`:1350` durable直接atomic_write。
- `integration_service.cpp:1357` writer后台atomic_write最新snapshot，失败重试并标采集缺口；它不是具有每条事件durable watermark的增量WAL。
- `integration_service.cpp:2743` buffered响应返回 persisted=false；`:2685` run.status按capture_dirty确认；`:2804` flush_capture仅等待采集落盘、不等待学习/策略评测。
- 文档 `docs/18-storage-and-recovery.md` 的“HTTP run.end成功表示已持久化”需限定durable模式；当前源码允许buffered，是汇报口径必须注意的漂移。

### 恢复与归档

- `integration_service.cpp:669` 启动读取runs；未closed的local/buffered记录标 incomplete + producer_interrupted，`:681` run.abort，`:695` 路径选quarantine。
- `integration_service.cpp:1599` recover_jobs恢复后台学习作业；这是学习状态恢复，不是复原未落盘事件，也不是自动恢复原业务Tool的执行位置。
- `integration_service.cpp:179` atomic_write：temp→write→file fsync→rename→directory fsync；文件fsync严格检查，目录fsync不严格检查。不据静态阅读声称断电故障已测试通过。
- `integration_service.cpp:844` maintain_runs：默认10000条，目标75%，每次最多移动64到archive/runs；run_file:839可继续读取归档。这只减少在线records，不释放磁盘。完整traces/incomplete quarantine与archive都仍占空间。TTL、磁盘byte预算、free-space门槛、物理删除未见于该函数。
- `agent_evaluation.replay_holdout` 是冻结评测/holdout的再验证；幂等重放请求是同request回执复用；L3 replan是当前循环策略；三者都不能等同业务崩溃续跑。

## 一、导师汇报最应先说清的结论

系统已经实现从真实 Agent 轨迹到经验库、受限行为策略、真实任务验证和版本交付的一条完整代码链路。其演化对象是经验正文/适用条件、动作准入、已有技能间的调度依赖和循环控制；当前组件不会训练基础模型权重。

在线运行从固定版本读取策略，在模型请求、动作派发、技能编排和下一轮循环四个真实边界介入。后台使用轨迹评估/反思积累经验，再通过 GEPA 搜索不同 L1–L3 策略。训练证据用于生成，验证成绩用于选择，最终冻结候选再进入 holdout 准入。

必须分开报告五个状态：**代码已实现 → 配置已开启 → 规则实际应用 → 同题效果改善 → 独立留出验收通过**。配置为 L3、节点 accepted、目录叫 published，均不足以单独证明后面三项。

## 二、L0–L4 应怎样讲

| 层级 | 当前实际能力 | 关键边界 | 能力证据 |
|---|---|---|---|
| L0 | 采集和评估，不修改本次 Agent 执行 | run/activity begin/end | `integration_service.cpp:2285–2351` 将闭合、采集完整与业务结果分开 |
| L1 | 将已批准且匹配当前 scope/任务的经验加入模型输入 | llm | `policy_runtime.cpp:495–564` |

## 三、在线执行：从冻结策略到真实回执

### 1. 一次 run 的策略怎样选定

`IntegrationService::Impl::start_run()` 加载当前用户私有 memory 和公共库视图，编译 `ShadowPolicySnapshot` 和 `RuntimePolicy`，再调用 `apply_agent_version()`（`src/service/integration_service.cpp:2033–2075`）。

`compile_runtime_policy()` 固定快照、批准经验版本、runtime options 和 policy_id；校验用户、会话、target scopes、能力等级、正文预算以及规则个数（`src/runtime/policy_runtime.cpp:309–356`）。之后本 run 读取该固定策略，不在线调用反思模型。策略内容是不可变对象，但 `PolicyRuntime` 为 L1 一次注入及 prepared query 保存少量可变缓存，不能称整个对象完全无状态或完全纯函数（`include/trajectory_evolution/policy_runtime.h:47–60`）。

三条部署路径（`src/evaluation/agent_evaluation_support.h:15–58`）：

- evaluation_version：绑定指定候选与 trial 身份。
- offline_version：加载离线策略包；用户/等级不匹配退至 L0，缺能力/scope/基础边界违反时报错。
- policy_evaluation_file：读取已评测发布版本；没有兼容版本时 L0，并写 `awaiting_evaluated_policy`。

若没有评测门禁配置，可以直接使用 current 编译策略（support.h:54–57）。这是一条接入模式，不能把它说成所有部署都强制验证后上线。

### 2. L1：经验影响模型输入

`ShadowRuntime` 用 task/state 中的词项、工具操作及结构化事实做有界匹配。它使用信息权重和词频做排序，而不是 embedding 或在线 LLM 语义检索（`shadow_runtime.cpp:792–835`）。

运行时只注入固定批准版本的经验；可用策略内 `experience_overrides` 改写正文/条件，也可 `disabled_injections` 停用；原来源 memory 保留（`policy_runtime.cpp:320–339, 531–561`）。同 run 每条经验只注入一次；原 prepared query 可幂等重放，不因交错查询丢回执（`policy_runtime.h:51–60`；`.cpp:514–560`）。

实际接入是 `packages/agentflow-runtime/src/agentflow_runtime/llm_call.py:89–104`：`_evolution.call()` 包住真正的 recorder.trace_call，发送增强后的 request messages。该接入当前条件是 coordinator v1，不能据此声称所有协调器版本、所有宿主都自动接入。

### 3. L2：动作和编排

动作边界按 action_id、operation、目标 scope、批准来源以及实际失败计数逐项 allow/reject。支持 schema 必填字段、明确批准的必填参数、失败/尝试预算等；不会扩大已有动作权限（`policy_runtime.cpp:565–617`；`control_generation.cpp:283–304`）。

编排边界用 `plan_schedule()` 给出依赖，实际并发/串行执行由宿主观察回写（`policy_runtime.cpp:618–630`）。生成的 schedule rule 只能作用于现有 batch 中的动作，必须有 source 和 `schedule.dispatch` 能力（`control_generation.cpp:543–562`）。

真实宿主位置：技能工具执行包在 `_evolution.call()` 中（`skill_executor.py:1359–1368`）；coordinator 的 run_skills 包在 `_evolution.call()` / `_evolution.dispatch()` 中，有 items/operation/receipt/results 的结构绑定（`coordinator_decide.py:1776–1798`）。不是仅依据模型 tool_calls 计划宣称动作已执行。

### 4. L3：停止或重新规划

coordinator/skill 的下一轮前都调用 `_evolution.allow_loop()`（`coordinator_decide.py:1362–1374`，`skill_executor.py:834–849`）。loop query 使用该分支 iteration、state fingerprint、重复动作/失败、是否可收尾和 pending actions 等事实。

当存在 pending actions、有效等级不足或宿主不支持 loop.decide 时固定 continue（`policy_runtime.cpp:644–648`）。无进展阈值、分支最大轮数、重规划预算等触发 replan/stop；重规划正文供下一次模型调用消费（`.cpp:684–720`）。生成规则必须依附已有基础 loop rule，并且不得放松基础预算（`control_generation.cpp:432–459`）。

### 5. “应用”怎样证明

`PolicyRuntime::verify()` 不直接相信宿主声称：

- L1/replan 检查 context 确实在实际请求内，且 transport_allowed 和 call_id 有效。
- actions 检查被拒绝动作在 skipped 列表中且不在 executed 列表中。
- schedule 按实际 events 推进依赖状态并要求结束、执行/跳过列表对应。
- loop 检查宿主确认的 stop/replan 与提案一致，且没有 pending actions。

代码：`policy_runtime.cpp:739–807`。**queries、triggered、applied、最终收益是不同概念**。

## 四、后台经验闭环：轨迹不是直接成为可执行规则

`task.end`/`task.abort` 关闭 run 后，完整轨迹 validate_trace；缺活动/采集缺口则 quarantined，完整且 auto_evaluate 为 true 则 pending（`integration_service.cpp:2285–2351`）。execution_status 与 business_status 分开，进程结束不等于业务成功。

`IntegrationService::process_evaluations()` 在独立学习线程处理批次，不让 Agent 在线打点进入阻塞评估路径（`.cpp:4131–4140`）。步骤为：

1. 原子落盘完整 trace，挑选达到时间/数量条件的用户批次（4131–4185）。
2. 规则/模型混合分析；独立轨迹分析可并行，身份、来源和缓存 fingerprint 逐项校验（4275–4440）。
3. `TrajectoryEvolutionPipeline::synthesize_reports()` 形成有证据来源、scope 和 revision 的候选（4444–4485；`evolution_pipeline.cpp:2200–2240`）。
4. `curate_memory_file()` 去重、检查相关/冲突并合并私有 memory，然后排队公共提炼（4486–4526）。
5. 新 memory revision 通知后台策略评测，但不改变已有 run 的冻结策略（4494–4500）。

单个分析失败写入 job.errors，其他独立分析继续；完整性和来源错误单独处理，不伪装成模型质量失败（4299–4311）。这只证明错误处理路径存在，不能替代故障注入验证。

候选准入不是模型 confidence 单独决定：无执行者/条件/正文、无来源支持分别拒绝；有反证标 conflicted；支持 Dialogue/Episode 数不足标 insufficient_support（`evolution_pipeline.cpp:668–748`）。

快照编译过滤 ownership、scope、target type、status 和 conflict（`shadow_runtime.cpp:344–429`）。支持 `require_validated_evidence` 门槛，但是否开启取决于配置；不能宣称所有 proposed 自动等于 validated。

私有/公共隔离：公共 store 的 application_id 必须匹配 agent，shared view user_id 必须匹配 user；跨私有/公共冲突关系需有固定内容 revision（`shadow_runtime.cpp:360–368, 508–528`）。共享提炼独立证据不足会 private_only，模型 distill + review 不通过则拒绝（`shared_memory.cpp:677–741`）。

记忆权威存储是 protobuf，JSON 是阅读视图；写入持锁、递增 revision、原子落盘和幂等重放（`evolution_pipeline.cpp:3948–4008`）。这些静态实现不等于任意断电都已验证无损恢复。

## 五、L4/GEPA：受限行为策略搜索

### 搜索对象

一个候选是完整策略 artifact，包括 L1 经验改写/适用条件/启停集合，L2 action_rules/schedule_rules，L3 loop_rules。生成器仅暴露获选组件和授权原语，不允许任意改写框架源码、增加工具权限或改变基础模型权重。

`control_generation.cpp:432–459` 保留基础 loop 限制；`gepa_strategy.cpp:591–627` 选择单组件以控制一次改动范围。`control_generation.cpp` 明确把可执行控制来源与固定批准 memory 绑定。

### 搜索步骤

1. 冻结 dataset、评测上下文、L0/current baseline 与 seed；要求 train/val/holdout 非空，所有任务 reviewed，seed 有批准来源（`gepa_search.cpp:10123–10143`）。
2. 选择逐任务优势前沿的父节点；保留必要探索多样性（`gepa_strategy.cpp:324–454`）。
3. 在 train 执行 parent，构造真实完整训练反馈，只让 train 任务进入反思（`gepa_search.cpp:6559–6563`）。
4. 反思生成获选组件，结构编译和预检；重复/没有可执行条件变化的草案记录 duplicate，不浪费 Agent 评测（`gepa_search.cpp:9643`）。
5. COMBEE 可对训练反馈 map/reduce；当前还有 `propose_full_pool()` 覆盖全部训练池的分片 map/reduce/final 逻辑，不能把旧 sqrt(n) 分组视为唯一模式（8704–8824）。
6. TRAIN screening 检查实际应用变化、同题质量/loop/resource 表现和收益证据（7548–7626）。
7. val 执行候选；只有在实际改变行为的验证题上存在局部收益才 accepted，可归属证据不够则 unobserved_changes（9775–9840）。
8. 合并使用共同祖先三方 merge，要求实际包含两个父分支贡献，不把复制单亲称为双亲融合（`gepa_strategy.cpp:560–588`）。
9. 最终冻结候选名单和 campaign，holdout_started 后不继续搜索。holdout 真实执行候选，仅可复用已锁定校验的 L0 基线（`gepa_search.cpp:11336–11393`）。
10. `AgentEvaluationService` 用统一门禁验收，先持久化发布状态再曝光 artifact，下一次 run 使用新版本（`agent_evaluation.cpp:1180–1202, 1334–1352`）。

### 质量、loop 和资源

目标质量使用已评估普通目标的加权完成比例，缺证据保留 quality_lower/quality_upper 和 coverage，critical 单独记录（`evaluation/goal_assessment.h:148–186`）。严格通过率仍独立报告。

GEPA fitness = quality - loop/token/latency 有界惩罚（`gepa_search.cpp:5640–5654`）；确定性硬检查失败会把质量归零（5631–5634）。反思可优先看到质量低、浪费高的成功题，而不仅仅是失败题。

最终门禁分别检查报告完成、有效覆盖、无执行/评分错误、真实同题配对、critical、质量门槛、无效 loop 同口径与覆盖、以及可配置的资源比率（`agent_evaluation.cpp:850–981`）。原生 min_quality_gain 是绝对加值（889–893）；实验入口的“相对提升 5%”是另一个明确口径，汇报不能混用。

默认 `gate.require_level_coverage=false`，只有显式打开才把全部生成规则或能力未实际观测视为拒绝（970–973）。因此“发布成功”仍须用应用次数解释到底用了哪层。

### GEPA 对 memory 的反向反馈

只交付搜索期间的 train 反馈，holdout 重测不生成第二份入库事件（`agent_evaluation.cpp:1196–1202`）。反馈按不同任务去重，正负证据形成 supported/regressed/conflicting/insufficient_support（`memory/gepa_feedback.cpp:205–226`）。validated 可转 memory VALIDATED，regressed 可归档；冲突可从 VALIDATED 回 candidate（301–316）。这比“每次成功就累计 confidence”更可追溯，但不等于已证明跨任务迁移。

## 七、当前真正仍需讨论的问题

| 问题 | 已确认边界 | 建议下一步 |
|---|---|---|
| 稳定收益还不足 | 代码有真实应用/同题收益检查，不能消除 LLM 执行随机性；单次净+分不等于策略因果收益 | 在少量代表题上重复配对，做去掉新增组件的消融，报告置信区间和失败类型 |
| L2/L3 新规则经常无机会或无收益 | 存在 untriggerable_controls/unobserved_controls/unobserved_changes；越过宿主打点或未命中都不能计收益 | 针对有真实 typed binding 的任务采集，先证明触发与执行，再试规模化 |
| 均值可能掩盖尾部退化 | `gepa_strategy.cpp:53` 注释称逐题，但 `loops_no_worse():55–75` 实际只检查逐题观测完整，最后比较均值 | 若研究目标要求尾部保护，应独立设计逐题退化/高分位门槛，不把现实现说成严格逐题非退化 |
| 筛选保护是启发式 | train 允许整体 loop/time/token 1.10 波动（7504–7526）；affected>=6 且质量退步占1/3拒绝（7528–7544） | 讨论误杀/漏放权衡，并使用冻结验证确认，不再因单个失败临时放宽门禁 |

## 十一、指标的精确口径补充
