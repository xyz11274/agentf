# Gap 06: JSON-RPC 协议健壮性

## 状态
⚠️ **部分实现**

## 问题描述

AgentFlow 的 JSON-RPC 实现使用**换行符 `\n`** 作为消息分割符，这在某些场景下存在风险。

## 当前实现

```cpp
// rpc_server.cpp:474-489 — 换行符分帧
while ((pos = recv_buffer.find('\n')) != std::string::npos) {
    std::string msg = recv_buffer.substr(0, pos);
    recv_buffer = recv_buffer.substr(pos + 1);
    // 处理 msg
}
```

## 风险分析

| 风险场景 | 是否可能 | 影响 |
|---------|:--------:|------|
| JSON 字符串含换行转义符 `\\n` | ❌ 不会（JSON 转义） | 无 |
| 手拼 JSON 字符串含真正换行 | ✅ 可能（用户手拼 `"key":"val\n"`） | **消息截断** |
| 格式化/美化的多行 JSON | ✅ 可能（开发者调试时复制粘贴） | **解析失败** |
| 二进制数据通过 JSON 传输 | ✅ 可能（Base64 不含换行，安全） | 无 |

## 其他分帧方案对比

| 方案 | 健壮性 | 复杂度 | AgentFlow 是否使用 |
|------|:------:|:------:|:-----------------:|
| 换行符 `\n` 分隔 | ⭐ | 低 | ✅ 当前使用 |
| Content-Length 头（LSP 标准） | ⭐⭐⭐ | 中 | ❌ |
| 长度前缀（4字节定长） | ⭐⭐⭐ | 中 | ❌ |

## 影响

- 当前在日常使用中（紧凑 JSON）没有问题
- 但如果客户端误发格式化 JSON 或消息体含换行，会导致解析错位
- 后续如果要扩展 JSON-RPC 给外部系统，需要升级分帧方式

## 建议方向

不急于改动，因为：
1. 当前所有内部生成的消息都是紧凑单行 JSON
2. 标准 JSON 库（`json.dumps`、`RapidJSON`）会转义字符串中的换行
3. 如果需要，后续可在连接握手时协商分帧方式
