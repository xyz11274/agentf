# 业务后端与30例开发验收

日期：2026-09-17。模型：现有配置的 `deepseek-v4-flash`。本次使用原始业务转换集中的固定30例、33轮，没有改用户输入、预期标签或原评分规则。它是开发代表集，不能代表全部1,074例通过率。

在浏览器、办公文件、知识库、提醒周期、Home Assistant/ADB 连接器和会话路由修复完成后，重新运行固定30例并启用 judge。原报告为15/30；33轮的规则通过率81.82%，judge通过率57.58%、均分3.36，意图集合完全匹配82.76%。独立业务状态检查为20通过、4失败、2个历史不足、1个确实缺输入、3个人工复核。它仍不是全量1,074例通过率。

四个明确失败点随后按原用例定向复核：用药提醒已创建并保留“剂量未提供”；无号码和指定号码两种充值计划均完整输出；台灯与风扇一次批量关闭。最终各定向运行的独立业务检查全部通过，充值计划最终 judge=4，家居 judge=4。定向结果用于证明具体修复，不回写或冒充同一次30例总分。证据位于 real-world-20260917-after/、real-world-fix4-20260917-075034/、real-world-fix2-20260917-075816/ 和 real-world-gui1-20260917-080237/。

业务包当前 Python 测试为114项通过；公共 SessionRouter 的相关 C++ 测试为51项通过。19项历史能力缺口探针全部未复现。

## 已落实的改动

- 家居有16台独立测试设备；控制实际改变状态，时钟持续推进窗帘、温湿度和耗电，支持故障、批量事务、查询与实际历史统计。
- 预约有测试医院/科室/医生目录、28天号源及跨用户共享库存；支持创建、查询、取消、原子改约、冲突检查和重试去重。
- 健康档案只保存明确的结构化健康资料，缺资料返回 `needs_input`，不能把更新请求或待补清单当病历保存。
- 原有真实天气、文件、图片、提醒继续使用；天气新增逐城市汇总，减少模型自己计算均值产生的错误。
- 评测新增独立业务状态检查，查设备、预约、事件和文件，避免只看模型回答是否“成功”。

这些家居/预约操作在独立业务测试系统执行，并不连接实体家庭或同名真实医院。

## 并发评测污染与当前处理

最初单daemon并发3时，发现辞职信用例的业务状态中出现GUI计划、充值用例下出现写作文件，同一物理session的两个身份在流程中发生错位。因此 `before-business-backends/` 与 `after-business-backends/` 仅保留为诊断证据，不能用两者的总体分数宣称提升。

当前脚本运行独立 daemon 且内部串行，以保持评测可复现。公共 `SessionRouter` 已加入路由预留和身份隔离，避免查找空闲会话与激活之间被另一身份抢占；相关 C++ 测试共51项通过。部署环境的长时间并发压力和异常恢复仍需单独验收。

所有运行使用的公共 `coordinator_decide.py` 源码哈希一致。后续运行会记录包内源码、配置、提示词及公共coordinator的哈希，便于复现。

## 尚需处理

- 多轮业务派发仍不稳定；部分回复含内部工作叙述，天气/徒步建议存在超出数据证据的表述。需要独立内容judge和业务复核，不能靠状态检查覆盖。
- 原始资料没有家居历史和具体就诊信息时，应请求资料/说明不足，不伪造历史满足预期。
- “湿度不大才设提醒”受真实天气影响；固定expected_skills可能与正确不执行的分支冲突，原标签未修改。
- ADB 与 Home Assistant 适配器已经实现，但当前没有物理设备配置；定位与实时算路、手机主动推送、真实医院账号、会员/原生播放器、原账户/私有业务知识、交易支付、可用视频生成模型仍缺外部资源或权限。
- 公共会话池身份隔离已有修复和51项相关测试；生产负载、进程崩溃和真实设备并发仍需部署专项验证。
- 未跑全量1,074例、未做独立LLM质量评分，不能宣称全量验收通过。
