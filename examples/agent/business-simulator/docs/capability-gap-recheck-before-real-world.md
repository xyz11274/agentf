# 业务能力缺口复查

日期：2026-09-17。结论：基础执行链路已经具备，但“有工具”还不等于“覆盖业务场景”。当前还有目录缺项、参数被忽略、任务修改缺失、历史数据不足及验收盲区；不能将失败全部归因于没有真实设备。

本轮重新对照三份原始 Excel、`benchmark/datasets/product.json` 和当前实现，运行了 **19 项隔离接口检查，19 项均复现对应缺口或边界限制**。这不是全量 Agent 评测，也不是 19 条业务用例的失败率；部分接口缺陷可能被模型通过规范化参数、补充文字或筛选结果暂时绕过。

检查脚本：[recheck_capabilities.py](../evals/recheck_capabilities.py)。机器证据：[capability-recheck.json](../evals/capability-recheck.json)，含输入、观察结果、关联用例、源文件哈希和完整候选清单。

## 一、当前环境内可以继续补的能力

### 1. GUI 计划本身还不完整

当前只有 `open/search/play/navigate/setting/order/recharge/send` 八类模板。

| 原用例 | 用户要求 | 当前缺口 |
|---|---|---|
| `TGZS_WYYL_015` | 芒果 TV 搜索《小巷人家》并收藏 | 搜索之后没有收藏动作 |
| `TGJK_WYD_002` | 应用市场安装豆包 | 搜索之后没有选择应用、发起安装和安装结果判断 |
| `CK_GUI_FHCK_00_055` | 腾讯视频“我的金币”签到 | `open` 只有打开 APP，没有进入指定页面并签到 |
| `CK_GUI_FHCK_00_104` | 对指定歌曲发表评论，并指定评论正文 | 没有评论对象、正文和发布步骤的专用表达 |
| `TGZS_YDYL_001` | 高德打车，确认车型与上车点 | 导航模板不能等同叫车流程；缺车型、上车点、叫车步骤 |

另外，用 `send` 传入具体正文，返回的 `taskPlan` 只有“填写用户指定内容”，正文并未保存；契约也没有独立收件人字段。`order` 只会搜索，再给出笼统的提交提示，缺选择商品/规格/数量/地址等参数。

**影响：** 原表很多用例只考步骤，补齐步骤就能提高真实的计划覆盖率；完成计划和真实点击仍须分别验收。模型在最终文本中补写步骤，不能证明保存的结构化计划完整。

定位：[contracts.py](../harness/business_sim/contracts.py)、[real_services.py：navigation](../harness/business_sim/real_services.py)。

### 2. 挂号目录与参数约束不完整

当前测试系统只有 5 家医院、12 个科室、2 个测试医生。库存、取消、原子改约已经存在，但业务数据中大量名字尚不能解析。

- 8 类目录外医院逐个调用均返回 `not_found`。例如 `SYS_DYT_01_081` 的协和医院、`SYS_DYT_02_015` 的安贞与同仁、`SYS_DYT_03_032` 的阜外医院。
- 神经内科、中医内科、心血管内科、体检均不在可用科室/服务目录；缺科室别名归一化。对应 `SYS_DYT_01_085`、`SYS_DYT_01_089`、`SYS_DYT_03_032` 等。
- `SYS_DYT_01_086` 指定“华西医院王医生”，但只存在“测试医师甲/测试专家乙”；需要目录检索与消歧，不能随意换医生。
- 号源记录没有费用、支付状态、院区/地址等字段，无法支持 `SYS_DYT_01_096`“我挂号花了多少钱”的实际查询。原规则若只验下发查询指令，可能发现不了信息缺失。

接口边界检查还发现以下**错误约束处理**，与“没有真实医院连接”无关：

| 隔离输入 | 实际结果 | 应有边界 |
|---|---|---|
| `date="明天晚上"` | 成功预约 `09:00` | 没有晚间号源就应明确返回不足，不能改约早上 |
| `date="明天下午3点"` | 成功预约 `14:00` | 保留准确时刻或澄清，不应静默丢失“3点” |
| 查询 `time_period="下午"` | 同时返回 `09:00` 与 `14:00` | 时段筛选必须生效 |

这三条是针对现有公开参数做的扩展边界检查，没有冒充原集中的三条已失败用例。模型可将部分日期转成标准格式，但当前契约明确允许保留自然语言日期，后端也需要校验。

**补齐方式：** 先扩展声明清楚的测试目录、别名和排班，完善约束校验；不需要先接真实医院。测试号源仍必须标明测试环境，不能冒充同名医院真实号源。

定位：[appointments.py](../harness/business_sim/appointments.py)。

### 3. 用药提醒缺少“修改既有任务”与复杂周期

`QA_JK_WYYL_011` 第一轮创建早晚提醒，第二轮说“饭后半小时吃”，预期明确要求调整提醒。当前没有 `reminder_update`，也没有进餐事件、相对时间规则或暂停/恢复接口。

对于饭后任务，应先取得饭点或进餐事件来源，再更新原任务；不能凭空把它解释成固定的 `08:30`，也不能新建后把旧提醒留下。

隔离检查还复现：

- 指定 `period="周一到周五"` 并给出截止日期后，接口成功创建 `FREQ=DAILY` 的日历，周末也会提醒。当前“仅每日重复”的限制没有被严格拒绝校验。
- `reminder_query` 传入指定 `id` / 药名，仍返回全部提醒，包括另一条已取消的提醒。模型可以再筛选，但接口并未兑现筛选参数。
- 没有稳定 `request_id` 时，重复调用创建会新增两条提醒；当前去重依赖调用方正确保留该字段，并非自动实现“同一次任务只执行一次”。

实际已具备的每日调度、持久化通知箱、重启补记和 ICS 不受这个结论否定。手机主动推送及已导入日历的取消同步，仍是另一层连接缺口。

定位：[reminders.py](../harness/business_sim/reminders.py)、[real_services.py](../harness/business_sim/real_services.py)。

### 4. 健康档案的筛选与信息保真仍不足

- 按患者或记录 `id` 查询，接口仍返回全部记录；两名测试患者的隔离筛选检查已复现。这里指同一业务作用域内的患者筛选，不代表不同用户可以互读数据库。
- 保存“咳嗽三天，尚未服药”时，症状被保留，但“尚未服药”因为包含“尚未”被当成占位词删除。这会误删真实的否定信息。
- 没有病历删除、版本追踪、原健康档案导入或报告识别能力。`origin=user_provided` 是标记，当前还不能自动证明每个字段确实来自用户原话。
- 导诊工具主要返回症状与已有病史，质量依靠模型；没有独立分诊规则引擎与医学质量专项验收。

**对评分的影响要分开看：** 如 `ZJ_JK_JKDA_003` 的原预期只要求下发查询指令，不要求列出诊断详情；上述筛选不足是实际业务能力缺口，不能直接据此宣判该原用例失败。

定位：[health_records.py](../harness/business_sim/health_records.py)、[real_services.py](../harness/business_sim/real_services.py)。

### 5. 家居习惯并不是完整的家居分析

设备控制已经能实际改变测试家庭状态，空调、窗帘和耗电也有时间演化。缺口主要集中在历史与分析：

| 原用例 | 需要的能力 | 当前实现 |
|---|---|---|
| `ZJ_JJ_XGCX_003` | 本周晚上空调使用最多的时段 | 没有时间窗口/夜间使用时长分析 |
| `ZJ_JJ_XGCX_004` | 上个月哪个电器耗电最多 | 只有设备累计耗电，没有按月历史账本与排行 |
| `ZJ_JJ_XGCX_005` | 开台灯时空调是否同时运行 | 没有设备状态时间线的联合分析 |
| `ZJ_JJ_XGCX_001` | 到家/离家习惯及指令 | 至少三天开关记录后，以开关时刻中位数推断；不是真实到家/离家检测 |

即使准备三天控制记录，`habits` 仍只返回上述中位数，不会因查询“上个月耗电”而改变分析。当前习惯响应还缺少原协议的 `operation_type=100053`；未传可选 `command_text` 时，历史生成的 `commandList` 可能是空文本。

原表对耗电、同时运行这两类问题的 `expected_behavior` 仍套用了 `modeList` 格式。因此，只验这个输出框架可能漏掉用户真正要的分析。需要补可审计的测试历史与相应断言，不能为了满足预期伪造用户的真实生活习惯。

定位：[device_world.py](../harness/business_sim/device_world.py)。

### 6. 影片详情、筛选与用户记忆

- 影片 `detail(index=2)` 返回整份片单，未选择第二部。`TGYJ_WYD_012` 需要回答第二部的故事，模型可利用上下文补答，但详情接口尚未完成该语义。
- 推荐的 `mood/exclude/count/family_friendly` 参数没有完整进入检索或确定性筛选，效果依赖模型；没有完整影片目录、演职员/评分/播放资源等字段及更新机制。
- 偏好按 `user+client` 保存；同一用户从新 client 读取时为空。这是已有作用域设计，不是本轮发现的用户间泄漏，但不能称为已具备跨会话、跨设备长期用户记忆。
- 原表声纹偏好用例目前通过前置偏好值准备，没有声纹识别、账户绑定、设备身份与授权链路。

定位：[real_services.py](../harness/business_sim/real_services.py)、[state.py](../harness/business_sim/state.py)。

## 二、需要资料、数据源或连接才能完整完成的能力

| 能力 | 当前能做什么 | 还缺什么 / 受影响场景 |
|---|---|---|
| 原业务知识 | 公开网页检索、模型回答 | 私有产品资料、版本和权益规则。例如 `SYS_DYT_03_278` 要求云手机上传应用的特定规则；不能将评测标准答案塞进运行时来代替知识库 |
| 账户和业务状态 | 查询公开资料、生成步骤 | 余额、流量、套餐、优惠、订单等经过授权的账户接口 |
| 手机 / APP 实际操作 | 生成计划与入口链接 | 设备连接、页面观察、点击输入、状态回读与失败恢复；目前没有可视化设备操作闭环 |
| 用户位置及路线 | 高德搜索/导航入口、避堵步骤 | 真实定位、目的地消歧、交通方式、实时路况和算路；无法凭链接证明最快路线或叫车成功 |
| 真实家居与医院 | 独立测试设备/号源的状态和事务 | 实体家庭控制器、真实医院预约/患者账户。测试执行与现实执行须继续明确区分 |
| 音视频播放 | 搜索与片单 | 授权媒体、播放器及播放/暂停/进度回执；歌曲播放同样缺执行器 |
| 主动通知、发送、交易 | 服务端通知箱、ICS、草稿与计划 | 手机推送、消息/邮件通道、真实订单及支付回执 |
| 时效性事实 | 天气模型接口、网页摘要 | 历史档案数据、可靠实时行情/库存/班次、原文核验。`DH_WD_LWWD_03_007` 的 2023 年历史台风场景超出天气适配器日期范围；不是普通未来预报 |
| 媒体理解 / 视频生成 | 已配置的真实图片生成 | 图片/音视频上传识别、语音链路；当前可用视频生成模型仍未确认。现有原集未发现明确的生成图片/视频任务，优先级不应高于已有业务需求 |
| 自定义流程与办公执行 | 文本生成、版本化 Markdown 文件 | 工作流定时/触发执行、办公应用、真实邮件或日程同步。保存计划不等于执行计划 |

这些能力中，有些可以用明确标注的独立测试环境验收接口和状态变化；只有真实设备或服务连接后，才能证明外部任务已完成。

## 三、仍会影响验收可信度的问题

1. **并发身份隔离未有修复证据。** 先前单 daemon 并发运行发现不同用例状态错位，目前通过多个独立 daemon、各自内部串行规避。本轮没有重新验证公共会话池，不能把规避当修复。
2. **条件任务与多轮派发需要独立验证。** 先前 `TGJK_YD2_010` 第二轮未派发 QA skill，天气任务还出现超出工具证据的叙述。真实天气改变条件分支时，不能用固定技能集合代替条件正确性判断。
3. **原业务输出协议尚未全覆盖。** 工具内部有 `UserOutputObject` 不等于最终回复完整保留或已下发客户端；操作码、字段、客户端执行回执缺少统一验证，习惯的 `100053` 缺失就是一个具体例子。
4. **共享设备与用户资产模型不完整。** 原表设备类型 1/2/3 共 698/232/144 例；当前适配器只把类型写成目标设备偏好，没有真正连接对应设备。独立 client 的全套新家庭也不等同同一用户跨设备访问同一家庭。
5. **状态判定范围有限。** 现有独立结果检查主要针对固定 30 例；此前 26/30 是未启用独立 LLM judge 的原规则结果，不能当成 86.7% 业务完成率。本轮 19 项接口检查也不能替代全量 1,074 例模型验收。
6. **标注不足会掩盖问题。** 727 轮缺意图，374 轮无实质预期；部分家居分析预期只校验通用输出结构。应保留原评分，同时另记状态、参数、条件、事实质量及“缺前置数据”，不能通过改标准答案制造提升。

先前运行证据和限制详见 [acceptance-30.md](acceptance-30.md)。

## 建议补齐顺序

| 顺序 | 工作 | 原因 |
|---|---|---|
| 先修正确性 | 预约时刻/筛选、提醒周期/修改、档案否定事实、必要操作码、稳定重试标识；复现并修复并发身份错位 | 防止接口返回成功却执行成另一个意思 |
| 再补大范围覆盖 | 测试医院/科室/医生目录、45 条命中用例所需的 GUI 步骤、可信原业务知识源 | 直接对应大量现有业务输入，无需先重建整套手机系统 |
| 再补持续状态 | 家居分时耗电与联合分析、历史准备机制、患者筛选、用户资产/记忆作用域、影片详情筛选 | 解决查询、多轮修改和长期使用能力 |
| 同步扩展验收 | 按场景抽样，检查实际状态及结构化输出，再做独立内容评分与全量回归 | 区分能力缺失、模型失误、前置数据不足和评分漏检 |
| 按验收要求接外部 | 手机自动化、定位算路、推送、真实业务账户、播放器/交易 | 只要求计划的用例先验计划；要求真实执行的场景必须补连接 |

## 复查方式

从项目根目录执行，使用已安装项目运行时的 Python：

```bash
python3 examples/agent/business-simulator/evals/recheck_capabilities.py \
  --output examples/agent/business-simulator/evals/capability-recheck.json
```

检查只调用本地接口，在临时数据库准备明确的诊断数据并自动清理；不调用模型或网络、不启动设备、不覆盖正在运行的业务状态，也不把评测预期送入 Agent。`gap_reproduced` 表示缺口已复现；本次没有修改这些运行时缺陷。
