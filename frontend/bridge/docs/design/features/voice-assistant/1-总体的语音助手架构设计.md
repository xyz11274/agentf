# 语音助手总体架构设计

> **层级**: L2 · `docs/design/features/voice-assistant/1-总体的语音助手架构设计.md`
> **状态**: 初稿
> **创建日期**: 2026-07-13

---

## 1. What

为 AgentFlow 系统增加**语音通话能力**，让 Agent 能够：
- **接听来电**：自动应答 PSTN 电话，与真人语音对话，完成业务目标
- **拨出电话**：主动拨打用户电话，获取信息或完成操作

**核心约束**：
- AgentFlow C++ 核心引擎**不做改动**，语音能力全部在 Node/Adapter 层实现
- 所有新增代码在 Python 侧（Bridge 或独立的语音进程）
- 通过 UDS 协议与现有 C++ 引擎交互

---

## 2. Why

### 2.1 业务价值

| 场景 | 说明 |
|------|------|
| 外呼通知 | 自动拨打电话通知用户订单状态、活动提醒 |
| 客服接待 | 用户来电由 AI 自动接待，完成常见问题解答 |
| 语音交互 | 用户通过电话与 AI 助手进行多轮对话，完成业务办理 |
| 问卷调查 | 自动拨出电话进行语音问卷调研 |

### 2.2 技术驱动力

- 2026 年语音 AI 技术已成熟（Qwen-Omni-Realtime GA、PersonaPlex 开源）
- 中文语音 ASR（FunASR-Flash 错字率 1.7% 全球第一）和 TTS（OmniVoice 600+语言）已可商用
- 与 AgentFlow 现有工作流引擎天然互补——编排层复用，语音层新增

### 3.2 四层职责

| 层级 | 组件 | 职责 | 是否改动 |
|------|------|------|---------|
| **C++ 核心引擎** | Master/Worker/DataBus/UDS | 工作流编排、节点调度、数据共享 | ❌ 不动 |
| **Bridge 层** | FastAPI 服务 | 通话管理 REST API、外呼任务管理、录音存档 | ⚠️ 新增端点 |
| **语音 Agent 进程** | Pipecat / 自建管线 | 音频处理、ASR/TTS/LLM 调用、VAD/打断逻辑 | ✅ 新增 |
| **电话接入层** | Twilio/Asterisk/声网 | PSTN 电话接入、SIP 信令、音频流桥接 | ✅ 新增 |

### 3.3 数据流架构

```
通话数据流 (按数据交换路径):
┌──────────┐  音频流   ┌──────────────┐  音频/文本  ┌──────────────┐
│ 电话用户  │←────────→│ 电话接入层    │←──────────→│ 语音Agent进程 │
│ (PSTN)   │          │ (Twilio/...)  │            │ (Pipecat)    │
└──────────┘          └──────────────┘            └──────┬───────┘
                                                          │ UDS JSON-RPC
                                                          ▼
                                                  ┌──────────────┐
                                                  │ AgentFlow    │
                                                  │ 核心引擎      │
                                                  │ (Workflow)   │
                                                  └──────────────┘

数据存储 (DataBus Key 设计):
  session_id / voice-agent / audio_raw       → PCM 音频块 (流式)
  session_id / voice-agent / vad_events      → VAD 检测事件
  session_id / voice-agent / transcript      → ASR 识别文本
  session_id / voice-agent / llm_response    → LLM 回复文本
  session_id / voice-agent / audio_tts       → TTS 合成音频
  session_id / voice-agent / call_metadata   → 通话元数据 (来电号码、时间、状态)
  session_id / voice-agent / recording       → 完整录音文件 (通话结束后写入)
```

## 4. 两种语音模式

这是语音助手的**两个核心方向**，可独立部署，也可按场景混合使用。

### 4.1 模式对比

| 维度 | 模式A: 管线模式 | 模式B: 全模态模式 |
|------|----------------|-----------------|
| **架构** | VAD → ASR → LLM → TTS | 语音直入 Qwen3-Omni → 语音直出 |
| **延迟** | 800ms-2s | 300-500ms |
| **成本/通(5min)** | $0.1-0.3 | $0.5-1.5 |
| **中文质量** | 组件级独立选型 | Qwen3 最佳 |
| **工具调用** | 复用现有 LLM 文本链路 | 受限于 Realtime API |
| **情感保留** | 丢失 (ASR→TTS 转换) | 保留完整语气情感 |
| **打断** | 需自建 | 内置 server_vad |
| **本地部署** | 全组件可本地 | 目前依赖云端 API |
| **最佳场景** | 强合规/低成本/复杂工具 | 客服/销售/情感交互 |

### 4.2 选择策略

```
用户需求
  │
  ├─ 强合规/数据不出域？         → 模式A (全本地组件)
  ├─ 成本敏感/量级大？           → 模式A ($0.1/通)
  ├─ 需要复杂工具调用/多步流程？   → 模式A (复用 LLM 工具链)
  ├─ 需要饱满情感/自然交互？      → 模式B (全模态)
  ├─ 需要实时打断/类人对话？      → 模式B (server_vad)
  └─ 既要成本又要体验？           → 混合: 简单场景用A，复杂场景用B
```

## 5. 与 AgentFlow 的集成点

### 5.1 集成矩阵

| AgentFlow 能力 | 在语音场景中的角色 | 集成方式 |
|---------------|-------------------|---------|
| **Workflow 编排** | 定义语音对话流程（接听→问候→识别意图→工具调用→回复→挂断） | 定义新的 Workflow DSL |
| **Session/Task 管理** | 每次通话 = 一个 Session，每次交互 = 一个 Task | 复用现有机制 |
| **DataBus (UDS)** | 语音 Agent 进程与 C++ 引擎之间的数据交换通道 | 复用现有 UDS 协议 |
| **Context 上下文回调** | 维护通话上下文（用户意图、历史对话、业务数据） | 复用现有机制 |
| **多语言扩展 (UDS)** | Python 语音进程通过 UDS 调用 C++ Node | 复用现有机制 |
| **Node 执行引擎** | 语音节点（ASR/LLM/TTS）作为标准 Node 执行 | 新增 Node 类型 |
| **工具调用 (MCP)** | 语音对话中查询订单、查询知识库 | 复用现有 MCP 机制 |

### 5.2 新增 Node 类型

| Node 名称 | 类型 | 职责 | 备注 |
|----------|------|------|------|
| `voice_input` | Python | 接收电话音频流，输出 PCM 数据 | 通过 UDS 或 WebSocket |
| `vad_detect` | Python | 语音活动检测，输出说话/静音事件 | Silero VAD / WebRTC VAD |
| `asr_transcribe` | Python | 语音转文本 | FunASR / Whisper |
| `llm_reason` | C++/Python | 文本推理，复用现有 LLM 链路 | 模式A 专用 |
| `tts_synthesize` | Python | 文本转语音 | OmniVoice / Fish Audio |
| `voice_output` | Python | 音频回传给电话通道 | 通过 WebSocket / RTP |
| `omni_proxy` | Python | Qwen3-Omni-Realtime 代理 | 模式B 专用 |
| `call_control` | C++ | 通话控制（接听/挂断/转人工） | 新增 C++ Node |

## 6. Session 生命周期映射

```
通话生命周期 ↔ AgentFlow Session 生命周期:

电话状态:     响铃     →   接通     →   对话中     →   挂断
               │            │            │             │
AgentFlow:     │    Session 创建         │    Session 清理
               │    route_key = 电话号码  │             │
               │            │            │             │
Task 状态:           Task 0 (问候)      Task 1..N     Task 结束
                                         (对话轮次)
```

**关键设计决策**：
- 通话 Session 的 `route_key` = 电话号码（来电显示或外呼目标号码）
- 每次通话对话轮次 = 一个 Task，由 Coordinator 管理
- 通话结束后清理 Session 关联的 DataBus 音频数据
- 录音文件单独持久化到文件系统，DataBus 中仅存引用

## 7. 监控与合规

### 7.1 必须的监控指标

| 指标 | 说明 | 告警阈值 |
|------|------|----------|
| 端到端延迟 p95 | 用户说完到听到回复 | > 1.5s |
| 打断失败率 | 用户打断但 AI 未响应 | > 5% |
| 通话中断率 | 非正常挂断 | > 2% |
| ASR 识别率 | 语音转文本准确率 | < 90% |
| 回声误识别率 | AI 回声被误判为用户输入 | > 1% |

### 7.2 合规要求

- **录音默认开启**：通话开始前提示"本次通话可能被录音"
- **录音存储**：完整音频 + ASR 转录文本，结构化存储
- **通话质检**：自动 ASR 分析 + 情感分析 + 关键词检测
- **数据保留**：按合规要求设置录音保留周期
