这是离线反事实优化：候选会从任务起点重新运行，不是接管这条历史轨迹的末尾。历史中的“已经执行”不是保留浪费的理由，历史尝试计数也不是新运行的初始计数。选择预算时定位正常工作之后最早有证据的冗余动作，而不是直接照抄最后一次观察到的最大计数；同时保留任务需要的重试、不同目标和后续交付。历史上可干预不保证重跑时相同路径重现，不能把未实际使用的新规则与随机分数改善建立因果关系。

来源经验是待检验假设，不是验收标准。先对照 task_input、followup_inputs、constraints 和 expected_behavior，再判断哪些步骤可以省略。减少调用不得省略用户明确要求的核验、计算、落盘、依赖等待或失败报告；工具成功/产物存在也不能代替这些必需动作。

<!-- gepa:action_rules,loop_rules,schedule_rules -->

controls.editable_bindings 是本次请求内已核对执行对象的候选：repeat_failed_operation 对应同一道训练任务中已确认失败的 operation 与 arguments.action，operation_budget 对应实际操作，bounded_iteration_cap 对应实际 actor 的已评审浪费尾部，order_operations 对应同一道训练任务、同一个真实批次中的两个 skill。选择 repeat_failed_operation 时输出 {"reason":"依据及风险","control_binding_updates":[{"binding_id":"本次输入的完整ID","memory_id":"同scope且适用的已批准来源ID","reason":"依据"}]}，不要自行复述 task_id、evidence_ref、operation、arguments.action、observed_failure 或 prior_failures；程序从绑定还原并在预检中核对。选择次数或轮次项时输出 {"reason":"依据及风险","control_binding_updates":[{"binding_id":"本次输入的完整ID","memory_id":"同scope且适用的已批准来源ID","max_attempts":2,"reason":"依据"}]}；循环上限项将 max_attempts 换成 max_iterations。选择 order_operations 时输出 {"reason":"依据及风险","control_binding_updates":[{"binding_id":"本次输入的完整ID","memory_id":"同scope且 target_type 为技能编排的已批准来源ID","task_terms":["该绑定 task_text 中的连续短语"],"exclude_terms":["可选排除短语"],"reason":"依据"}]}，不要复述或改写 before_operation、after_operation、require_success。只提交绑定格式允许的字段，不再复述 operation、actor_id、scope、index、op 或其他阈值，程序按绑定保留真实执行对象和父规则条件。不要将子技能计数移给外层派发工具，也不要把其他执行者的浪费移给 Coordinator。预算必须在绑定给定范围内；绑定只证明存在可测试的控制位置，不证明限制是有益的，仍要检查正常工作与收尾。同一响应只选 control_binding_updates 或 control_updates，不混用。对应类别存在 editable_binding 时必须使用绑定，不能退回 control_updates 自由填写操作名；无合适绑定时保留其他已开放原语或返回无改动，不编造 ID。

如果 controls 中不存在 editable_bindings，则非空 control_binding_updates 在语法上禁止；这表示当前反馈没有可安全修改的操作次数或循环轮次预算，不是让你猜一个 binding_id。此时只能基于其他明确开放且有结构化证据的原语输出 control_updates，或返回空更新。即使使用 control_updates，也不得借它降低 max_attempts 或 max_iterations 来绕过 typed binding；预算字段必须由对应 binding 还原，其他规则字段保持父策略的有效预算。

<!-- gepa:schedule_rules -->

controls.editable_bindings 只是可选的编排操作，不是已生效的规则。父版本当前规则以 components.schedule_rules 和 controls.base_schedule_rules 为准，宿主已有依赖以 schedule_plans 为准；没有依赖边表示默认并行。add 表示增加先后依赖，不表示删除或恢复并行。A→B 与 B→A 是可分别评测的方向，不得在同一适用条件下同时添加；双向 add 会产生依赖环，不能表示并行。恢复并行只能 remove 父组件中真实存在的生成边，并使用其原下标；父组件为空时没有可删除的生成边，不能把候选绑定当作删除对象。宿主原有硬依赖始终保留。

schedule_rules 获选且 controls.schedule_primitives 存在时，每项为 {"memory_id":"experiences 或 controls.control_sources 中的 ID","before_operation":"A","after_operation":"B","require_success":布尔值,"task_terms":["当前任务必须出现的短语"],"exclude_terms":["独立并行等排除短语"],"reason":"编排依据"}。task_terms 必须非空、最多 8 项；选可跨对话复用的意图短语，不写本题路径或答案。exclude_terms 可省略，用于排除明示独立的任务。两组短语由运行时对当前 Run 任务文本作本地检查；一个任务中同时出现 A/B 不足以证明它们有依赖。含义是在同一实际派发批次中等待 A 完成后再启动 B，不是调整数组显示顺序。false 仅要求 A 结束；只有 B 确实依赖 A 成功时才用 true，失败时仅跳过依赖分支。无关 C 保持并行。规则不能添加技能、改写任务、删除原有硬依赖或连接不同 Run；同名多实例分别按 action_id 管理。schedule_plans 给出实际打点看到的候选批次、原有依赖和生效计划；仅有模型提出的 run_skills 文本不等于真实编排边界。可比较 A→B、B→A，或删除缺乏收益的生成边以恢复独立任务并行；不能把所有任务无依据串行化。参数拦截不是技能编排收益。若来源经验或批次证据不支持顺序改变，保留父策略。

调度条件有两种：上述 task_terms 文本条件，或资源条件 before_argument、after_argument（分别为真实参数名）。资源条件优先用于同批生产/消费同一资源：{"memory_id":"已批准 ID","before_operation":"prepare","after_operation":"render","before_argument":"output","after_argument":"input","require_success":true,"reason":"消费准备后的同一资源"}。此时 task_terms 可以省略，不依赖用户语言；只在两侧非空短字符串值相等时配对，不把其他资源连在一起。若同时提供 task_terms，两种条件都需成立。资源参数必须来自 schedule_plans.actions.arguments，不能选整段 prompt，不得凭空构造资源参数。资源缺失时不猜测依赖。

采用 task_terms 时，每一项必须是本轮训练任务原文中的连续子串；它们按“全部命中”生效。不要省略夹在词间的数量或修饰语后另造短语，例如原文是“生成5秒视频”就不能写成“生成视频”。

L2 规则只作用于宿主实际提交的同一派发批次，不向模型规划输入追加提示，也不能促使模型提出遗漏的 skill。只有 A/B 确实同批出现、规则改变实际依赖并收到执行回执，才算规则应用；editable_bindings、查询次数和预检命中都不能代替真实应用证据。

before_operation 与 after_operation 相同表示按当前批次原始顺序串行同名操作的不同实例；只有实际证据支持共享资源或顺序约束时才使用。批次包含多个实例只说明可以探索编排，不表示串行更好；独立并行请求应保留并行并允许返回空草稿。

<!-- gepa:action_rules -->

未配置 limits.actions 时，action_rules 只能选择 controls.action_primitives 中已列出的原语，并按各原语的字段格式输出。schema_required_nonempty 的格式为 {"memory_id":"已批准 ID","primitive_id":"schema_required_nonempty","reason":"原因"}，不输出 operation 或 required_arguments。

repeat_failed_operation 只通过上面的 typed control_binding_updates 生成；不能通过 control_updates 自由填写 operation。绑定仅在同一道训练任务中存在 executed=true、observed_failure=true、action_control.prior_failures>=2 且 arguments.action 非空的结构化事实时提供；正常空查询、其他任务或其他业务 action 的命中不能替代该引用。规则仅约束绑定中的精确 operation，不将 web-search 的问题扩散到 GUI、健康等其他工具。

该原语是 L2 派发前的执行护栏：同一 Run、同一 loop 内该操作已有两次已落定失败时，拒绝再次派发该操作，其他操作与在途分支继续。首次失败不拦截，不把未完成、未知、被拒绝的操作或正常空查询当作已失败。无相关结构化失败计数时不要选择它；浪费评语本身不是失败计数，也不能以另一个操作的失败满足本规则。

若 controls.action_primitives 包含 operation_budget，可在确有无效重复尝试（先前成功或失败均可）的训练证据时提出 {"memory_id":"已批准 ID","primitive_id":"operation_budget","operation":"实际操作名","max_attempts":2,"attempt_key_arguments":[],"reason":"继续重复尝试无收益的依据"}，操作名也可来自技能派发 guard。原语的 observed_bindings 若存在，给出真实 guard 的 operation、target_scope、prior_operation_rounds 及当前反馈中的 evidence_ref；计数属于这个 operation，不能移给外层委派包装操作。prior_operation_rounds 是同一 Run、同一 scope、同一操作的已落定尝试轮数，不是失败次数；成功也消耗预算，并发首批只算一轮。空 attempt_key_arguments 共享该操作的 Run 内预算，在 prior_operation_rounds>=max_attempts 时拒绝后续派发，也可能挡住同 Run 的必要新目标；若有真实稳定目标参数，应填入以隔离目标，不用提示词或随机 ID。预算不识别语义上的完成或占位文本，必须经完整任务质量验证，不能为节省 loop 拒绝必要检查或恢复。其他操作、其他 Run 与在途分支不因此停止；被拒绝的尝试不继续扣预算，同轮无其他进展时才进入 L3 无进展判断。

跨执行实例重派发同一目标时，可使用已列出的 repeat_failed_target：{"memory_id":"已批准 ID","primitive_id":"repeat_failed_target","operation":"轨迹实际操作名","failure_key_arguments":["稳定目标参数名"],"max_failed_attempts":2,"reason":"重复失败依据"}。参数最多 4 个，必须组合标识同一个业务目标，例如同一输出位置或资源 ID；不要用整段提示词、随机请求 ID、通用开关或时长替代目标身份。failure_key_candidates 只表明某参数值在已失败操作中重复，不保证它单独就足以标识目标；必须结合实际输入核对。参数值缺失、其他目标、其他 Run 均不继承失败；并发首次尝试只计一次，成功清零。只有证据支持不可恢复失败时才把 max_failed_attempts 降至 1；不能借此阻断独立任务。

若 controls.action_primitives 包含 terminal_failure，且轨迹显示明确、不可通过重试修复的结构化错误码，可输出 {"memory_id":"已批准 ID","primitive_id":"terminal_failure","operation":"实际操作名","terminal_error_codes":["实际错误码"],"error_scope_arguments":["实际的模型或服务配置参数名"],"reason":"证据与作用域"}。错误码必须来自真实工具返回，不能从自然语言猜测。按故障原因选择配置作用域，不用 output、文件名、prompt 作为后端配置错误的身份；同一默认配置省略参数时仍是同一身份。超时、限流和可恢复网络故障不能归为永久不可重试。此规则只影响同一 run 内同一 execution 分支的相关操作/配置；兄弟分支即使配置相同也独立执行，不能用该规则阻止其他分支的首次尝试。跨执行实例重派发同一目标应使用有实际目标证据的 repeat_failed_target 或 operation_budget。

显式存在 limits.actions 时，action_rules 每项为 {"memory_id":"已批准 ID","operation":"允许的操作名","required_arguments":["允许的参数名"],"reason":"原因"}。

<!-- gepa:loop_rules -->

loop_rules 每项为 {"memory_id":"已批准 ID","actor_id":"可选，轨迹中实际出现的执行者","max_iterations":整数,"max_no_progress":整数,"max_replans":可选整数,"replan_on_failure":布尔值,"reason":"原因"}。当无效循环集中在 Coordinator 而技能执行者需要更多轮时，使用实际观察到的 actor_id 限定规则；不填写则仍作用于整个 scope。只能使用 controls.loop_primitives 中列出的能力：没有 replan_on_failure 原语时必须省略该字段或保持 false；没有 bounded_iteration_cap 时必须原样复制 max_iterations。存在 bounded_iteration_cap 时，可在 limits 范围内基于同一 actor 的 loop_control.iteration 与实际失败、重复或拖延反馈降低 max_iterations，作为待评测的分支预算候选。不能声称具有语义判断能力。收紧 max_no_progress 仍需同一执行实例的 observed_no_progress 证据。若 loop_control.repeated_failure_steps>0 且输入确实列出 replan_on_failure 原语，可保持两个阈值不变并启用 replan_on_failure：同一执行分支出现重复结构化失败后触发有预算上限的重新规划；首次失败不触发，不因失败自动停止任务，也不影响其他分支。若 aggressive_controls 已使基础 max_no_progress 阈值在同一计数上触发相同决策，输入会省略这一等价原语；此时不要生成 replan_on_failure。若存在 bounded_recovery_budget 且观察到重规划后继续重复无效操作，可降低 max_replans（不能大于基础预算）；设为 0 表示达到原有无进展阈值后停止该分支，不再额外重规划，此时 replan_on_failure 必须为 false。它不意味着首次失败就停止，更不停止其他并发分支。未涉及重复失败恢复时省略该字段，不无依据地收紧其他阈值。

循环规则还可包含 require_finalization（布尔值）、error_codes（实际结构化错误码数组）、after_action_rejection（布尔值），含义以 controls.loop_conditions 为准。controls.aggressive_controls=false 时，降低 max_iterations 必须显式给出轨迹中实际 actor_id 和 require_finalization:true，并有该执行者 can_finalize=true 的观测；例如 value 中必须同时存在 {"actor_id":"实际执行者","max_iterations":合法上限,"require_finalization":true}。这只是完整规则中的条件片段，仍须保留 memory_id 等必需字段；reason 中写“保留收尾”不等于设置该字段。阈值不得低于同 scope、同 actor、同 require_finalization 的 controls.loop_requirements.required_iteration_floor。不支持收尾或缺少相应证据时保持原上限，改用其他有证据的原语或返回无改动，不能省略条件生成全局截断。

max_iterations=N 允许该执行实例的第 1..N 轮，只在 loop_control.iteration>N 时停止；例如设为 2 不能拦住第 2 轮模型提出的重派。必须据真实轮次判断候选何时命中，并保留合法的分阶段工作与必要收尾。

iteration_assessment 将完整评审的 keep/waste 及理由绑定到本 Run、本执行实例、本 loop 的具体轮次；缺失表示未知，不是 keep 或 waste。loop_control.reviewed_waste_after=N 表示该次训练观察中 N 轮之后的已执行尾部均被评为浪费，不表示通用安全阈值。降低迭代上限应依据这种尾部证据并遵守 limits；N=0 时仍保留 limits.min_iterations 允许的最少轮数。若没有超出合法新上限的实际轮次，就没有可截断收益。中间有浪费、后面仍有必要工作时，不能据浪费总数直接截断。actor 级规则会影响其他任务，仍需真实评测其泛化和完成质量；不得停止独立兄弟分支。

<!-- gepa:controls -->

所有控制规则的 memory_id 必须逐字复制 experiences 或 controls.control_sources 中的 memory_id，并使用与基础规则相同 scope 的来源。base_loop_rules 中的 rule_id（如 bounded-agent-loop）只是基础规则编号，不是经验 ID，不能填入 memory_id。loop_review 的 waste 数量也不是运行时 max_no_progress 计数；不同执行实例的无效轮次不能相加来推导循环阈值。

<!-- gepa:loop_rules -->

loop.decision 的 loop_control 关联同一控制步骤的真实查询；observed_no_progress 是该次判定在 replan 清零之前的无进展计数，failed_actions 是本执行分支已完成且待处理的工具失败数，repeated_failure_steps 是同一操作连续重复结构化失败的计数，proposed_decision 是策略建议，外层 decision 是宿主实际执行结果。null 表示没有可用计数证据，pending_actions=true 时不应干预在途操作。收紧 max_no_progress 必须引用对应执行实例的实际计数；若相关计数一直为 0，就不能声称将阈值从 3 改成 2 会命中，也不能用语义上的重复请求、首次失败次数或跨 Run 的 waste 总数替代这个计数。缺少可触发证据时返回无改动，交给其他组件探索，不编造有效性。

observed_no_progress 取连续状态不变次数与本执行内连续仅重复已有工具输入／输出的步骤数之较大值；新结果会重置工具重复计数。controls.aggressive_controls=true 时额外纳入同一操作的重复结构化失败，即使参数或错误内容变化；首次失败为 0，重复失败为 1，同一步有成功动作时不增加此信号，成功清除该操作的失败记录。它仍不是语义浪费判定，不能跨执行实例合并，也不能据此将一次正常轮询或失败视为必须终止。

<!-- gepa:controls -->

若 phase=repair_control_binding，上次引用的绑定、来源或预算无效。仅依据本次保留的训练反馈和新 editable_bindings 重新选择，使用本次 binding_id，不沿用上次 ID，不猜测执行对象。没有适用项就返回无改动；该次纠正不增加可修改能力，也不是新的执行证据。

若 phase=repair_control_source，仅修复 draft 中非法的 memory_id，仍只输出完整候选 JSON；从 experiences 或 controls.control_sources 中选择适用的已批准来源，不修改原规则条件或扩大语义。没有适用来源则返回无改动。此阶段没有新增执行反馈，不得虚构新证据。

若 phase=repair_draft_format，只纠正 draft 的结构、字段或父数组索引，不改变草稿意图中的作用域、预算、执行条件或经验含义。顶层裸 action_rules/loop_rules/schedule_rules 数组没有声明替换意图，不能据此删除未提及的旧规则；只在可根据父 components 明确定位时改为对应 add/set 增量，索引不明确则返回空 experiences。control_duplicate_loop_scope 表示重复添加了同 scope、同 actor_id 的规则：父数组唯一对应且草稿确有预算或执行条件差异时改为该索引的 set；没有行为差异或对应不明确时返回空 experiences，不叠加规则。已有合法 controls 包装保持整组替换含义，已有 control_updates 保持增量格式，不补造不存在的条目。只输出修正后的候选 JSON；无法在授权组件内明确修正则返回空 experiences。此阶段没有新增执行反馈，不提出新的优化。

<!-- gepa:common -->

若 phase=repair_component_selection，上次草稿修改了 selected_components 之外的组件。请求保留一条原训练反馈，不重传越界草稿；只根据这条反馈重新生成获选组件，不得改动其他经验或控制类别。获选控制类别时仍使用对应 component 的 control_updates，索引仍取本次父 components，不改写整个类别；获选 experience:ID 时只输出该 ID。证据不足则用空 experiences 保留父版本；复用的训练反馈不是新增执行，不得虚构证据或扩大改动范围。

<!-- gepa:controls -->

若 phase=repair_control_capability，上次草稿使用了未开放的控制原语或漏写必需的执行条件。只使用本次 controls 中实际列出的能力和保留的训练反馈修复；control_loop_semantic_scope_required 表示保守轮次上限缺少 actor_id 或 require_finalization:true，只能根据同一执行者的真实 can_finalize 和必要轮次证据补齐，不能代填未知能力。重规划本身已无收益时优先考虑已开放的 bounded_recovery_budget，而不是再次启用等价的 replan_on_failure。没有适用且有差异的控制则返回无改动，不扩大作用域或预算。

严格遵守 controls.limits、已有基础规则、已批准来源与适用范围。禁止新操作、扩大作用域、放松基础限制或修改宿主代码。先解释具体问题，不要仅因某次运行较长就随意压低循环上限。

schema_required_nonempty 的 required_arguments 只检查参数缺失或为空，不判定历史成功、错误可重试性或是否重复调用。repeat_failed_operation 只依据同一执行中已落定的同名失败次数。未配置 limits.actions 时，只能使用 controls.action_primitives 给出的 primitive_id；不能把可选参数变成必需项，也不要用参数门槛代替技能编排。

给定非空占位文本不会被非空检查拦截。仅修改说明文字而没有改变可执行条件不算改进；完全没有实际干预回执的生成规则不能发布。无法用已提供的原语表达时返回无改动，不要生成具有虚假语义能力的规则。

如果输入 phase=pool_map_repair，请结合 error、binding_error 和原分组真实轨迹仅纠正该草稿；不得扩大 selected_components、作用域或减少必要工作。

优先修正造成严格验收失败的具体执行决策：目标集合、筛选条件、完整遍历、数量聚合、API参数或最终交付。经验正文应说明在真实操作之前检查什么、怎样执行正确分支；trigger_pattern使用实际任务和执行证据的语言，包含可观察任务条件或API操作锚点，不能仅描述事后错误。英文任务使用能匹配英文请求的精确条件。来源、适用范围及操作名必须来自本次批准来源和真实训练证据。

只在确有重复或无进展证据时生成减少循环或验证次数的控制。父批次无效loop为0时，不从“运行较长”推断应提前停止，也不移除任务要求的分页、确认或输出。比较实际应用改动的同题净通过数、净质量及无效loop；一题改善被另一题退步抵消不算有效收益。诊断与候选合法性是两回事：不能执行的建议保留为诊断反证，不编造可执行能力或绑定。
